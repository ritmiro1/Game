# Все применимые технические варианты

Это отдельный экспериментальный проход **непосредственно из оригинала 480×636**, а не ещё одно пережатие прежней 4K/16K-копии. Старые файлы не заменяются. Пункт «найти менее сжатый исходник» не выполнен: такого файла нет, поиск другой записи не проводится.

## Что создаётся

Десять **полных по длительности** сравнительных MP4 720×1280 с одинаковым кадрированием и настройками H.264. Для всех, включая контроль, используется одна рабочая сетка ×2 и одинаковый финальный масштабировщик, чтобы разница простой интерполяции не маскировалась под эффект фильтра. Разница между мягкими фильтрами может быть небольшой.

| Номер | Суффикс | Содержание |
| --- | --- | --- |
| 01 | `reference` | Контроль: только интерполяция, поля и экспорт, без улучшения изображения |
| 02 | `multiframe` | Субпиксельная многокадровая реконструкция с обратной проекцией |
| 03 | `deblock` | Небольшие корректировки слабых границ исходной 8-пиксельной сетки |
| 04 | `motion-denoise` | Временное шумоподавление с компенсацией движения и отбрасыванием несовпадений |
| 05 | `chroma` | Сдержанная обработка цветовых каналов с защитой яркостных границ |
| 06 | `deblur` | Три ограниченные итерации коррекции размытия с оценочным ядром |
| 07 | `adaptive-sharp` | Ограниченная яркостная резкость с отсечением шума и ореолов |
| 08 | `color` | Экспериментальная постоянная цветокоррекция в пределах ±1% и слабая тоновая кривая |
| 09 | `stable` | Временная стабилизация **только добавленной обработкой разницы**, не самой движущейся сцены |
| 10 | `balanced` | Все перечисленные методы в сдержанной комбинации |

02–09 — изолированные методы, а не последовательные поколения сжатия. 09 использует 07 как исходную обработку для проверки стабилизации её остатка. Вариант 10 также выгружается в 1080×1920 и 2160×3840, плюс отдельная облегчённая 720p-копия для просмотра. Все конечные экспорты идут из общего **FFV1 lossless** промежуточного файла; архивный 4K не делается из сжатого 720p.

## Многокадровая обработка: что она означает

Используются текущий и два настоящих соседних кадра, без создания новых моментов времени. DIS optical flow оценивается в обе стороны, затем проверяется возвратное совпадение движения, фотометрическая разница, выход за края и большие перемещения. Ненадёжные и перекрытые участки не смешиваются. При заметной смене сцены соседнее наблюдение отбрасывается.

На сетке ×2 выполняются две итерации ограниченной обратной проекции: оценка изображения проецируется на сетку наблюдения соседнего кадра, ошибка возвращается назад с весом доверия. Изменение яркости ограничено тремя уровнями 8-битного сигнала относительно кубической интерполяции. Используются только наблюдения исходника; нейросетевая или генеративная модель не применяется.

Это **эксперимент, а не доказанное восстановление настоящей недостающей детализации**. Ошибки optical flow всё равно возможны. Слабые фильтры могут быть незаметны, более сильные — ухудшать текстуру. Оценочное ядро размытия и предположение gray-world о цвете не гарантированно соответствуют съёмке. Поэтому методы доступны отдельно, а итоговая комбинация не объявляется объективно лучшей.

## Что сохраняется

- Все 1518 исходных кадров, без интерполяции и пропуска.
- Полная исходная картинка. Пропорции сохранены с округлением до чётного пикселя; 9:16 дополнен чёрными полями. Новая сцена по сторонам не создаётся.
- Видеотаймкоды нормализуются к 30 кадрам/с с исходным начальным смещением около 66,656 мс. Проверяется отклонение от этой сетки менее 1 мс. Исходное чередование интервалов 2999/3000/3001 тиков не копируется буквально.
- AAC-пакеты копируются и сравниваются по SHA-256; нормализация звука не применяется.
- Старые 4K, 16K и копии для просмотра остаются без изменений.

Размер 4K здесь означает выходной холст, а не нативную детализацию 4K. Новая анатомия, новые действия и промежуточные кадры не создаются. Улучшение содержимого за пределами исходного изображения не заявляется.

## Запуск и проверки

```bash
python -m pip install -r video-tools/requirements.txt
python -m unittest discover -s video-tools -p 'test_*.py' -v

# Все стадии, включая 4K и ZIP. Временные мастеры держать вне репозитория.
python -u video-tools/enhance_variants.py \
  --source video-tools/input/armorypass-ejoy.mp4 \
  --output-dir /path/outside/repository/video-variants

# Шесть кадров для проверки всей цепочки. Такие результаты не упаковываются для выдачи.
python -u video-tools/enhance_variants.py \
  --source video-tools/input/armorypass-ejoy.mp4 \
  --output-dir /path/outside/repository/smoke --test-frames 6
```

`--stage render|exports|validate|package` позволяет повторить нужную стадию. `--no-4k` пропускает тяжёлый экспорт, но не является настройкой для полной публикации. Полная публикация требует 13 MP4, архив и отчёты. Уменьшенные тестовые результаты отмечены `test_only: true` и не публикуются workflow.

Валидация каждого MP4: полное строгое декодирование всех кадров и звука, число кадров, монотонность и диапазон видеотаймкодов, AVC profile/level, размер кадра, BT.709, fast-start и SHA-256 исходных AAC-пакетов. `render-analysis.json` содержит измеренные различия **до сжатия**, не оценки качества; уменьшение разницы не доказывает улучшение. Реальная плавность на устройстве пользователя не измерена.

Workflow `video-variants.yml` запускается **только на текущей ветке** отдельным `jobs/variants-20261110.json`. Не нужно менять задания 16K или прежних копий для просмотра. После тестов и валидации результаты загружаются в отдельный draft-релиз, все размеры и GitHub SHA-256 сверяются, и только затем релиз публикуется без изменения latest-релиза приложения. Большие результаты и FFV1-мастер в Git не попадают. В ветку сохраняются только лёгкая копия и отчёты с проверкой общего лимита 128 MiB.

ZIP содержит десять сравнительных 720p MP4, описание и отчёты. Отчёт внутри ZIP не содержит хеш самого ZIP во избежание циклической зависимости; внешний `variants-validation.json` дополнен этим хешем. Full HD и 4K находятся отдельно, чтобы не раздувать архив.

## Публикация

Планируемый отдельный релиз: `video-variants-20261110-cc989019`. До появления успешного запуска и проверенного отчёта эти ссылки не считаются подтверждением готовности файлов. Результат публикации сохраняется в `publication-variants.json`; ссылки для скачивания — в `downloads/README.md` после успешной сборки.
